# AIPassport v0.1.5

The executable targets **macOS arm64**, requires separately installed Google
Chrome and an authenticated webchat profile, and remains licensed under
**AGPL-3.0-only**. The executable is ad-hoc signed, not notarized.

## Changed

- Prompt contract v25 separates `CLIENT INSTRUCTIONS` (response types, examples,
  and working flow) from caller-owned `HARNESS INSTRUCTIONS` and the offered
  tool catalog. Exact repeated instruction bodies and skill/MCP catalogs are
  declared once, preserving role order and distinct task/result content.
- Keyed submissions include the short every-turn guard without adding a second
  copy when initialization already contains it. Keyless input is unchanged.
- Repair, provision, and recovery submissions use fresh turn keys. Key-mismatch
  and eligible no-response retries reference the failed submission with
  `RETRY OF: <key>` instead of replaying its original task body. Validation uses
  the submitting key, and derived turns retain their origin-key linkage.
- Exact offered tool names can appear as envelope types with either nested
  `input` or flattened arguments. AIPass converts these into standard client
  tool calls without a per-harness tool-name registry. The harness owns argument
  validation, permissions, execution, and results; conflicting argument forms
  and invalid action attribution are rejected before dispatch.
- Completed tool-named response chains no longer wait for DOM fallback solely
  because the response type is a tool name. Browser-attempt completion remains
  separate from tool execution, and ambiguous-submission protection is retained.
- Recognizable missing-type answer envelopes are decoded as chat text while
  preserving attribution, reasoning, and estimated usage. Unknown ordinary
  answer-shaped JSON retains its existing text behavior.
- Processing browser tests reuse a suite-owned Chrome process with a fresh
  context per test, keeping transport handling active through teardown without
  increasing deadlines or weakening assertions.

## Known limitations

- Tool normalization is not a guarantee of valid model output, successful tool
  execution, or reliability across every harness or model. Reserved envelope
  types retain their canonical meaning; a tool sharing one of those names must
  use `type: "tool"` with its explicit `name`.
- OpenCode title generation and main-task requests can share a session identity
  and trigger repeated initialization with different instructions. Caller-side
  title isolation was not installed; that behavior remains unresolved.
- Context retention, changed-instruction replay, and large tool catalogs remain
  subject to upstream webchat behavior. Instruction deduplication is exact, not
  semantic. Usage remains estimated, not billing-accurate.
- An already-pending ambiguous submission is not cleared by normalization; the
  provider continues to fail closed rather than blindly resubmit possible work.
- Configuration and stored-data schemas are unchanged; no migration is required.

## Installation and rollback

Stop the provider, then use `aipass-browser-provider update --version 0.1.5` or
the [maintained installer](../../site/install.sh) with `--version 0.1.5`.
Verify `aipass-browser-provider --version` prints `0.1.5` before restarting.
Updating does not restart the service.

To roll back, stop the provider and install `0.1.4` with the same configuration
and state directories. Do not delete browser credentials or session state.
In-memory Responses continuation IDs do not survive a restart. Rollback restores
the prior version's prompt and envelope handling and its documented limitations.
