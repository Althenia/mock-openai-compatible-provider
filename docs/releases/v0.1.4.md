# AIPassport v0.1.4

The executable targets
**macOS arm64**, requires separately installed Google Chrome and an authenticated
webchat profile, and remains licensed under **AGPL-3.0-only**.

## Changed

- Prompt contract v25 declares the envelope guard only in initialization.
  Every submission still carries `TURN KEY:`, but task, result, repair, and
  correction submissions do not prepend the harness protocol again.
- Initialization puts the response `type` enum, response matrix, payload
  examples, and simple working flow under `CLIENT INSTRUCTIONS`. Caller-owned
  agent/workspace rules and skill/MCP/tool catalogs are separate under
  `HARNESS INSTRUCTIONS`. Exact repeated instruction bodies and
  `available_skills`/`mcp_instructions` blocks use a single declaration with
  references preserving the original role positions. Exact repeats in lowered
  `system-update` messages are omitted from task projection; distinct progress,
  ordinary user text, and tool results remain intact.
- A new session sends one keyed initialization submission containing the
  role/action protocol, ordered caller instructions, and the full
  offered tool catalog with schemas; its `READY` reply is internal. Later task
  and action-result submissions send only their keyed delta. Both APIs retain
  omitted initialization state in bounded process-local session state; explicit
  instruction updates or an empty instruction string replace or clear it.
  Per-turn `tool_choice` changes current action availability without removing
  the retained full initialization catalog.
- Bound turns in both instruction modes send only the latest user/result delta,
  plus the turn key and any required tool-choice constraint.
  Full conversation history is sent on initial/recovery/compaction submissions.
  Corrective turns reference the startup schema and latest delta instead of
  replaying the full role, tool contract, or conversation.
- Chrome runs headed by default so the user owns the window, watches turns live,
  and closes tabs themselves (`AIPASS_BROWSER_HEADED=0` opts back into headless).
  Cancelled and failed turns no longer close their tabs; the next turn resumes on
  the kept page after re-checking the durable binding and prompt contract. Only
  genuinely unrecognized responses still retire the page.
- Admitted and validated streaming requests now begin with the standard Chat
  assistant-role chunk or Responses `response.created`/`response.in_progress`
  records before browser work completes. Authorization, request validation,
  reservation, and capacity preflight errors remain normal HTTP errors before
  SSE starts. Custom `aipass.stage` data records have been removed: generic
  Chat clients validate every data payload and reject `{ "stage": ... }`.
  Progress means actual assistant output within the agent turn, not provider
  lifecycle labels. Browser, authentication, and safety failures after streaming
  starts use the endpoint's error format (nested Chat `error` objects or typed,
  sequenced Responses error events), without successful completion;
  non-streaming HTTP errors are unchanged.
- Agent-turn progression retains whole-response validation: actual attributed
  DOM reasoning and complete current-key thinking envelopes may be emitted
  before backend completion. Answers and tool calls remain withheld until the
  complete response validates. Captured text is passed incrementally to that
  validation path without repeating it at completion; a conflicting DOM
  replacement fails instead of rewriting already-observed output.
- The webchat safety-filter block (`ขัดกับระบบความปลอดภัย`) fails the turn
  immediately instead of falling back, waiting, or repairing. Detection runs on
  each stream's accumulated chunk boundary and on current DOM progress, even
  before settlement. It takes precedence over wrong-key retry and all
  repair/argument-correction paths. The attempt records a definitive failure.
  No automatic retry or successful finish follows the block; the caller may
  revise the prompt and retry explicitly.
- Malformed chat/thinking envelopes whose free-prose text contains unescaped
  quotes are salvaged instead of leaking raw envelope syntax to the client.
  The repair is narrow: chat/thinking types only, valid envelopes bypass it,
  and tool-bearing envelopes stay strict.
- Missing-type answer envelopes with a nonempty turn key, an `answer_*` ID,
  nonempty text, and no action fields are decoded as chat text instead of
  leaking their JSON wrapper. Turn attribution, tool validation, reasoning,
  and estimated usage remain in place for Chat and Responses, JSON and SSE.
- Complete bare and `TURN KEY`-prefixed envelope chains are validated before
  single-envelope repair, preventing an invalid trailing action from being
  absorbed into repaired chat text during strict validation after reasoning
  progress. Single malformed chat recovery and non-strict behavior are retained.
- Serial startup orchestration is extracted from browser I/O. Priming tests
  use Bun's native mocks and controlled promises to check request order,
  response gating, identity reuse/commit, and failure/cancellation propagation
  without Chrome, an HTTP server, temporary profiles, or timing sleeps.

## Known limitations

- Delta-only bound turns and kept-open tabs rely on the webchat retaining prior
  context in the same conversation. If the backend truncates, drops, or restarts
  context silently, a bound turn may answer from stale or missing history; the
  contract-change/recovery replay can restore supplied context, but corrective
  turns do not replay the complete history or schemas.
- Combined initialization sends every offered schema once, so large tool
  catalogs add initialization size, latency, and quota use. Retention and
  compliance across initialization and later delta-only turns have not been
  verified against a live backend.
- Instruction deduplication is exact, not semantic: differently worded rules
  and non-catalog partial prose overlaps remain untouched to preserve meaning.
  Initialization-only guards and missing-type answer recovery have local
  regression coverage but have not been verified against an authenticated
  upstream webchat.
- Resuming a user-repurposed tab re-navigates to the bound chat URL, discarding
  whatever the user navigated to in that tab.
- The safety-block matcher keys on the Thai block phrasing. A reworded filter
  message would miss detection and fall through to the previous fallback path.
- The calling client still owns permissions and tool execution. AIPass does not
  load another application's workspace or agent instructions.
- Responses continuation IDs remain bounded, single-use, and process-local.
  Restarted or expired IDs require authoritative history in a new request.
- Configuration and stored-data schemas are unchanged; no migration is required.

## Installation and rollback

After publication, stop the provider before installing version `0.1.4` with the
[maintained installer](../../site/install.sh) and its `--version 0.1.4` option.
Verify `aipass-browser-provider --version` prints `0.1.4` before restarting.
Once v0.1.4 is installed, use `aipass-browser-provider update` for later releases,
or `update --version VERSION` for a pinned installation. See
[update safety and custom destinations](../operations.md#update-and-restore).
The executable is ad-hoc signed, not Developer ID signed or notarized. Updating
does not restart the service.

To roll back, stop the provider and use `--version 0.1.3`, then restart with the
same configuration and state directories. Do not delete browser credentials or
session state. In-memory Responses IDs do not survive a restart. Rollback also
restores 0.1.3's prompt-delivery behavior and documented limitations.
